# ESP32 — веб-управление + метадата Arylic (компаньон к Mega-прошивке)

Отдельный проект для платы **ESP32**, компаньон к основной прошивке аудио-блока на
Arduino Mega 2560 (`https://github.com/egor-avksentyev/260422-030547-megaatmega2560`).
Портирует наработки из ветки `experiment/ethernet-arylic-webctl` того репозитория
(Ethernet/W5500 на самой Mega) на Wi-Fi/ESP32 — отдельный чип, а не второй интерфейс
на Mega.

## Почему снова ESP32, хотя раньше выбрали Ethernet-на-Mega

В `ETHERNET_ARYLIC_WEBUI_PLAN.md` (лежит в Mega-репозитории) решение было в пользу
Ethernet-модуля W5500 прямо на Mega — один чип, одна прошивка, не боится ни
металлического корпуса (Wi-Fi там глушится), ни просадок 5В от реверса моторов.
Это решение и то обоснование остаются в силе как записанная история — этот
ESP32-проект не отменяет его, а обслуживает отдельное, более позднее решение
пользователя вернуться к варианту с отдельной платой на Wi-Fi. Значит, часть рисков
из старого плана актуальна и здесь, и их нужно держать в уме:

- **Металлический корпус** — если он экранирует Wi-Fi, нужен модуль ESP32 с выводом
  антенны наружу (версия с разъёмом U.FL/IPEX + внешняя антенна), а не с
  PCB-антенной на самой плате. Проверить сигнал по месту перед тем, как закрывать
  корпус окончательно.
- **Просадка 5В при реверсе моторов** — та же самая линия питания, тот же риск, что
  обсуждался для W5500 (см. `MOTOR_REVERSE_BRAKE_MS` в `hardware_settings.h`
  Mega-репозитория). У ESP32 всплески тока на передаче Wi-Fi даже больше, чем у
  W5500 (до ~800мА против пары сотен мА) — см. раздел "Питание" ниже.

Что изменилось по сравнению с исходным ESP32-вариантом из плана: раньше речь шла
только про метадату Arylic с Mega "которая просто слушает готовые данные по UART".
Здесь на ESP32 переезжает **обе** функции из ветки `experiment/ethernet-arylic-webctl` —
и метадата, и веб-управление (см. ниже).

## Архитектура

Два независимых чипа вместо одного:

- **ESP32** (этот проект) — держит Wi-Fi, HTTP-сервер для веб-страницы управления
  с телефона, HTTP-клиент к локальному API Arylic. Ничего не знает о состоянии
  меню Mega.
- **Mega** (основной репозиторий) — как и раньше, всё управление железом
  (моторы/реле/NeoPixel/OLED/ИК/энкодер). Из этого проекта в её сторону идёт
  **только приём** по UART — см. "Mega только слушает" ниже. **Важно: приёмная
  часть на самой Mega пока не реализована** (осознанное решение при создании этого
  проекта, 2026-09-10) — пока это не сделано, команды с веб-страницы никуда не
  доходят, физически ничего не переключается. Протокол ниже — контракт для того,
  кто/когда будет делать этот приёмник.

```
Телефон/браузер --HTTP--> ESP32 --UART (только TX)--> Mega (пока не слушает)
Arylic (HTTP API) <--HTTP-- ESP32
```

### Mega только слушает — почему нет обратного канала

По решению пользователя ESP32 ничего не получает от Mega обратно — только шлёт.
Это значит:

- Нужен ровно один провод данных (ESP32 TX → Mega RX), не два.
- **Level shifter не нужен** — см. раздел "Согласование уровней UART" ниже,
  обоснование именно в том, что линия однонаправленная и идёт "вверх" (3.3В → 5В-вход),
  а не "вниз".
- **Известное ограничение**: `/status` на веб-странице не может показать настоящее
  состояние Mega (какой пункт меню открыт, громкость, mute) — ESP32 этого просто не
  знает. Сейчас `/status` показывает только то, что знает сам ESP32: состояние Wi-Fi
  и последнюю отправленную команду (см. `web_control.cpp`, `lastActionSent`). Если
  позже понадобится настоящий статус на странице — единственный способ: завести
  обратный канал Mega TX → ESP32 RX, и тогда на этой линии **level shifter/делитель
  обязателен** (см. ниже) — ESP32 GPIO не 5В-толерантны.

## Протокол UART (`mega_link.h/.cpp`)

Простые текстовые строки, `\n`-терминированные, 115200 бод, `SERIAL_8N1`:

- `CMD:<letter>\n` — команда, `<letter>` один символ:
  `R`=right, `L`=left, `E`=enter, `U`=up, `D`=down, `M`=mute, `P`=power, `S`=set
  (тот же словарь действий, что был у `WEB_ACTIONS` в `web_control.cpp` на
  Mega-ветке `experiment/ethernet-arylic-webctl` — тогда это были `IR_RIGHT`/`IR_LEFT`
  и т.п.; кто будет писать приёмник на Mega — самый прямой путь сделать `switch` по
  этой букве и вызвать те же функции, что сейчас вызывает `executeMenuCommand()` в
  `remote_control.cpp`, третьим источником ввода после пульта и энкодера, по тому же
  принципу дублирования, что описан в `CLAUDE.md` того репозитория).
- `META:<text>\n` — метадата Arylic, формат `"Artist - Title"` — до
  `MEGA_LINK_META_MAX_LEN` (40) символов, без переводов строк (`config.h`).

### Формат ответа Arylic API — подтверждён на реальном устройстве (2026-09-10)

Живой запрос к `https://192.168.1.139/httpapi.asp?command=getPlayerStatus` (порт **443**,
самоподписанный сертификат — обычный **HTTP на 80 у устройства закрыт**, проверено live)
вернул плоский JSON без вложенности, ~370 байт:

```json
{"type":"0","ch":"0","mode":"31","loop":"4","eq":"0","vendor":"spotify:playlist:...",
 "status":"play","curpos":"121699","offset_pts":"0","totlen":"230040",
 "Title":"4A757374204C697374656E","Artist":"41626F76652026616D703B204265796F6E64",
 "Album":"536972656E73204F662054686520536561","alarmflag":"0","plicount":"0",
 "plicurr":"0","vol":"100","mute":"0"}
```

`Title`/`Artist`/`Album` — **hex-encoded строки** (пары ASCII-hex-цифр = байты UTF-8),
не обычный текст напрямую. Пример выше раскодирован: `Title` → "Just Listen",
`Artist` → "Above &amp; Beyond". `pollArylicMetadata()` (`arylic_metadata.cpp`) теперь
реально разбирает это — `strstr`-поиском по плоскому JSON (полноценный парсер не нужен,
формат слишком простой), декодирует hex и шлёт `META:Artist - Title` на Mega, но только
когда `"status":"play"` — иначе ничего не шлёт (поведение на паузе/стопе — см. открытый
вопрос ниже).

**Это и есть настоящая, подтверждённая на реальном железе причина, почему нужен именно
ESP32, а не Mega/W5500**: этот API отвечает ТОЛЬКО по HTTPS, а штатная `Ethernet.h`/
`EthernetClient`, которую использовал `experiment/ethernet-arylic-webctl` на Mega, вообще
не умеет TLS — у ESP32 есть `WiFiClientSecure` из коробки (`client.setInsecure()`, раз
сертификат самоподписанный). На Mega-ветке `pollArylicMetadata()` пыталась достучаться на
порт 80 (закрыт), каждая неудачная попытка ненадолго блокировала `loop()` и сбивала
состояние веб-сервера (W5500) — эта функция там отключена (закомментирована в `main.cpp`,
2026-09-10) именно из-за этого.

## Потеря связи и реконнект

`wifi_setup.h/.cpp` следит за Wi-Fi событийно (`WiFi.onEvent`), не поллингом раз в N секунд —
состояние берётся из `ARDUINO_EVENT_WIFI_STA_GOT_IP`/`_DISCONNECTED`. При разрыве связи
(роутер перезагрузился, устройство вышло из зоны действия и т.п.) переподключение идёт с
нарастающей паузой: первая попытка через `WIFI_RECONNECT_BASE_MS` (2с), дальше пауза
удваивается на каждой неудачной попытке до потолка `WIFI_RECONNECT_MAX_MS` (30с) — не
долбит роутер попытками каждые несколько секунд, если тот недоступен надолго. Сразу после
успешного подключения (`_GOT_IP`) пауза сбрасывается обратно к базовой.

Downstream-эффекты потери связи уже учтены остальным кодом, ничего дополнительно чинить не
пришлось:
- `pollArylicMetadata()` проверяет `wifiIsConnected()` в начале и просто ничего не делает,
  пока связи нет.
- `/status` веб-страницы уже показывает `wifiIsConnected() ? "Wi-Fi OK" : "Wi-Fi отключён"`
  (хотя сама веб-страница в этот момент, конечно, тоже недоступна — открыть её можно только
  пока связь есть).
- `WebServer` просто не получает новых клиентов, пока Wi-Fi не поднят — не падает и не виснет.

Не реализовано (не обязательно, но если понадобится): смена своего IP после переподключения
(новый DHCP-лиз может выдать другой адрес) — тот же открытый вопрос про mDNS, что и раньше.

## Настройка

1. `cp src/wifi_credentials.h.example src/wifi_credentials.h`, вписать свою сеть.
2. `pio run -t upload`
3. `pio device monitor` — в логе будет IP-адрес, который ESP32 получит по DHCP.
4. Открыть `http://<IP>/` с телефона в той же сети.

## Железо и питание

### Почему это не тривиально: пики тока Wi-Fi

ESP32 в момент передачи по Wi-Fi даёт короткие (десятки-сотни микросекунд), но
существенные броски тока — до **~500-800мА**, заметно больше, чем у W5500 из
исходного Ethernet-плана. Просадка питания в этот момент, наложившись на уже
известную по этому проекту просадку линии 5В при реверсе моторов, может вызвать
brownout-reset ESP32 (спонтанные перезагрузки, обрывы Wi-Fi) — тот же класс проблемы,
что уже был учтён для W5500 (`network.cpp`, "Power W5500 from the NeoPixel 5V tap").

### Список необходимого

1. **Плата ESP32** (DevKitC / NodeMCU-32S или аналог). Если корпус металлический —
   предпочесть вариант с внешней антенной (разъём U.FL/IPEX) вместо PCB-антенны на
   плате.
2. **Питание 5В** — забирать не напрямую с линии, которая держит H-мосты моторов, а
   с той же точки, что уже проверена в Ethernet-плане для W5500 (NeoPixel 5V tap) —
   меньше связи с просадками от реверса моторов.
3. **Стабилизатор 5В→3.3В**:
   - На большинстве dev-плат ESP32 уже есть свой встроенный LDO (обычно AMS1117-3.3
     или аналог) на входе 5В/VIN — для типового хобби-применения обычно достаточно,
     но у AMS1117 посредственная реакция на быстрые броски тока (transient response).
   - **Обязательно добавить ёмкость** рядом с платой ESP32: электролит
     **470–1000мкФ, низкий ESR** (танталовый/полимерный лучше обычного алюминиевого)
     на входе 5В, плюс керамика 100нФ параллельно; то же на выходе 3.3В, если пин
     выведен. Это прямая мера против как раз описанных выше бросков.
   - Если на практике всё равно будут брауноуты/самопроизвольные перезагрузки при
     активной передаче — заменить встроенный LDO платы внешним с лучшим откликом:
     качественный LDO (например ME6211C33, MIC5219) с той же обвязкой конденсаторами,
     либо понижающий импульсный (buck) модуль (например на MP1584EN) на выход 3.3В —
     больше запаса по току, меньше греется при постоянной просадке 5В→3.3В.
4. **Общий GND** между Mega и ESP32 — обязательно, без этого UART и вообще любые
   логические уровни не имеют смысла.
5. **Один провод данных**: ESP32 TX2 (`MEGA_LINK_TX_PIN`, GPIO17 по умолчанию, см.
   `config.h`) → Mega RX2 (пин 17 на Serial2 — свободен на Mega, не занят другими
   модулями; см. `hardware_settings.h` в Mega-репозитории). RX2 самого ESP32
   физически никуда не подключать (Mega не отвечает, см. "Mega только слушает" выше).
6. **(Опционально, дешёвая страховка)** — резистор 330Ом–1кОм последовательно на
   линии ESP32 TX → Mega RX. Не нужен для самого согласования уровней (см. ниже),
   но ограничивает бросок тока на случай, если этот пин на Mega когда-нибудь по
   ошибке окажется настроен на выход. Не мешает передаче на 115200 бод.
7. Кабель/разъёмы для UART (TX, GND) и питания (5В, GND) между платами.

### Согласование логических уровней UART — почему level shifter не нужен

Линия одна и идёт в одну сторону: **ESP32 TX (3.3В) → Mega RX (5В-логика)**.

- Порог входа HIGH (V_IH) у ATmega2560 при Vcc=5В — минимум 0.6×Vcc = **3.0В** по
  даташиту. У 3.3В есть небольшой запас сверху (0.3В) — не огромный, но рабочий:
  связка "3.3В-выход → 5В-Arduino RX без шифтера" массово используется на практике
  (ESP8266/ESP32 ↔ Arduino UART-мосты — стандартный, устоявшийся приём) и работает
  надёжно в подавляющем большинстве случаев. Level shifter "вверх" (3.3В в приёмник
  5В-логики) в этом направлении — действительно необязательное усложнение, решение
  пользователя (2026-09-10) обоснованно.
- **Обратное направление НЕ подключено** (см. "Mega только слушает" выше) — если
  когда-нибудь понадобится (например, ради настоящего статуса на веб-странице),
  для линии Mega TX (5В) → ESP32 RX (3.3В) шифтер/делитель **обязателен**: у GPIO
  ESP32 нет 5В-толерантности, прямое подключение к выходу Mega рискует физически
  повредить пин. Минимум — резистивный делитель (например 1кОм/2кОм), надёжнее —
  полноценный level shifter (74LVC245, готовый модуль на BSS138 и т.п.).
